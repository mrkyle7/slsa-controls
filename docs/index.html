Introducing IAST. Start it as an evidence source, not a gate. Instrument two or three tier-one JVM or .NET services in pre-production only, run the agent during existing functional and DAST suites, and use the output for one purpose: deciding whether a vulnerable dependency is actually reachable. That reachability verdict becomes the input to a VEX statement, which is what lets you defensibly deprioritise a critical CVE in a package you ship but never call. Expand to production instrumentation only after you have a performance budget agreed with the service owners, and never make IAST a promotion blocker until its false-positive rate is understood — a blocking control that teams learn to route around costs you more than the control gains.

The CVE clock

Provenance is immutable; vulnerability state is not. An artefact verified clean on Tuesday is not clean on Friday because a CVE was published on Wednesday. This is the part of the control that has a time dimension, and it needs a different design from every gate above.

T0

Advisory published

The clock starts at disclosure, not at the next build and not at the next scan run. Feed ingestion latency is itself a control metric: measure the gap between advisory publication and the bank knowing about it.

T0 + minutes

Match against stored SBOMs

Every artefact digest ever promoted has an SBOM on file. Matching happens against that store, not by rebuilding or rescanning. This is why S2 matters — an artefact that never registered itself is invisible to this query.

T0 + hours

Blast radius

Resolve affected digests to running instances across Linux, Windows, internal and external cloud. This is the query the regulator and the incident bridge both ask, and it is the current red gap in the control map.

T0 + 1 day

Exploitability triage

KEV, EPSS, reachability and exposure feed an SSVC decision that produces an action, not a score. A defensible "not affected" is worth more than a rushed patch cycle, but only if the reasoning is recorded as a signed VEX statement rather than a ticket comment. See the exploitability model below.

Severity SLA

Remediate and re-verify

Remediation produces a new digest, new provenance, new VSA. The old VSA is not revoked by the fix; it is superseded. Deployment gates must prefer the newest valid VSA for a resource, or the clock never actually stops.

Continuous

VSA staleness

A verification summary carries the time it was verified. Treat that timestamp as an expiry: past a defined age, admission requires re-evaluation even if nothing else changed. This is what turns a point-in-time gate into a standing control.

Design consequence. The spec's verification model is point-in-time by construction, and warns that a VSA does not protect against compromise of the verifier. For CVE tracking you need two things it does not give you: an expiry policy on verification results, and a persistent digest-to-instance index. Both are bank-built, both belong to the inventory pillar, and neither exists today.

Exploitability

Severity alone generates an unworkable queue. The public pattern is to layer independent signals and end at a decision, not a number. Nothing below is bank-invented.

CVSS

Intrinsic severity

What the flaw could do if reached and exploited. Asset-agnostic and context-free, which is exactly why it cannot be the whole answer. Use base metrics as an input, not a ranking.

KEV

Observed exploitation

CISA's Known Exploited Vulnerabilities catalogue. Binary and high-confidence. Presence in KEV should short-circuit the tree straight to the shortest remediation clock.

EPSS

Predicted likelihood

FIRST's probability that a CVE is exploited in the wild in the next 30 days. Re-scored daily, so a finding's priority legitimately changes without the artefact changing — another reason verification results need an expiry.

Reachability

Is the code called

IAST during test execution, plus static call-graph analysis where available. This is the signal that most reduces queue volume and the one that requires the most investment to trust.

Exposure

Where it runs

Internet-facing or internal, data classification, mission criticality, which cloud. This comes from inventory, not from the scanner, which is why the S5 gap blocks the whole model.

SSVC

The decision

CISA and CMU SEI's decision-tree method. Walks decision points — exploitation status, automatable, technical impact, mission and well-being impact — and emits one of four actions: Track, Track*, Attend, Act. Adopt the deployer tree, calibrate the mission-impact points to HSBC's own tiering, and publish the tree so the outcome is reproducible and auditable.

Why a tree and not a score. SSVC produces an action with a traceable path through named decision points. That is the difference between telling a regulator "this was a 7.5 so we scheduled it" and showing the specific reasoning that led to a deferral. Publish the calibrated tree as a versioned artefact in the same repo as this control.

Recording the outcome: VEX

The machine-readable output of triage is a VEX statement bound to a product identifier. OpenVEX defines four statuses and, for not_affected, requires a fixed justification label or an impact statement. Only not_affected suppresses a finding; the others document without filtering.

OpenVEX statuses and the five not_affected justification labels.

The distinction that governs everything below. not_affected is an engineering claim about the artefact — falsifiable, evidence-backed, and it does not expire on a calendar. A waiver is a risk decision about an artefact that is affected — it expires, it needs an owner senior enough to carry it, and it must be scarce. Conflating the two is how exception processes rot: everything gets filed as "not exploitable" because that route has no expiry and no approver.

Waivers and exceptions

The hard problem: at ingress there is no consumer, no environment and no exposure, so there is no context in which a risk decision can be made. The answer is not to make the decision earlier with less information — it is to defer it and carry the obligation forward.

The obligation pattern

An ingress decision that cannot be made becomes a travelling obligation rather than a blocker or a blanket pass. The package is admitted with under_investigation attached to its PURL. Every artefact that later resolves that package inherits the open obligation through its SBOM. The obligation surfaces at the release gate, where context finally exists, and is discharged there as either a justified not_affected or an owned, expiring waiver. Nothing is waived in the dark, and nothing silently blocks a team that has no way to answer the question yet.

Scope is explicit

Every waiver names vulnerability, component, product digest, environment and expiry. A waiver without all five is not a waiver, it is a hole.

Signed, not ticketed

Waivers are signed attestations bound to a digest, evaluated by the same policy engine as everything else. If it lives only in a ticket, the gate cannot enforce it and the auditor cannot verify it.

Expiry is not renewable by default

Renewal requires new evidence, not a repeat of the original argument. Second renewal escalates a tier. Third goes to the control owner with the service's remediation history attached.

Approval tier tracks the decision

SSVC Act and anything in KEV cannot be waived below executive level. Track and Track* can be self-approved by the service owner within budget.

Waiver budgets

Each service carries a cap on concurrent waivers. Exhausted budget blocks new non-emergency releases. This is what stops the fast path becoming the only path.

Emergency path exists

A documented break-glass with a fuse measured in days and automatic re-review. Teams route around controls that have no emergency path, so provide one and instrument it.

Anti-abuse instrumentation. The metrics matter more than the policy text: waivers granted per service per quarter, median age of open waivers, proportion of releases using the emergency path, renewal counts, and the ratio of not_affected determinations to affected findings per team. A team whose suppression ratio is far above the estate average is either unusually good at reachability analysis or is mislabelling risk acceptance as a technical determination, and the data tells you which to go and ask about.

Promotion paths

We do not control every production deployment, so a deploy-time gate cannot be the only enforcement point. Instead, enforce where we already hold authority — the registry — and make an artefact's location a consequence of its evidence.

Design constraints

Location is derived state

The attestation set decides the path; a reconciler moves the artefact. If the path itself becomes the security property, then whoever holds copy permission between paths is the real control — a much weaker thing to defend. Movement between paths is itself a signed, attested event.

Scope what creates an obligation

If every open finding routes to protected, everything lands there and gated capacity becomes the bottleneck. Only KEV, SSVC Act and Attend, and unreviewed packages create one. Review this threshold quarterly against the actual split.

Ingress stays open for development

Block at promotion, not at pull, except for packages unacceptable at any tier. A developer who cannot pull will vendor the source or build locally, which removes the proxy's visibility entirely — strictly worse than admitting the package with an obligation attached.

Route out under pressure

An ungated production service needing a hotfix for something sitting in protected is the first real incident with this design. The emergency waiver path must admit it on a short fuse, or teams will route around the registry.

Pull telemetry as a proxy

Where deployment is ungated, registry pull events give an approximate digest-to-environment map. Weaker than admission control — a pull is not a run — but often the fastest route to a blast-radius answer for the ungated estate.

Coverage is the headline metric

Percentage of the production estate on gated deployment, by risk tier, with "would have blocked" counts published for the remainder. That number justifies the investment and answers the regulator better than silence about the gap.

Joining it up — don't build this from scratch

The linking problem across SBOM, provenance, scan results, VEX and waivers is solved in public. Evaluate before building.

GUAC

OpenSSF incubating project that ingests SPDX and CycloneDX SBOMs, SLSA and in-toto attestations, OSV, OpenVEX and CSAF VEX into one graph with a GraphQL API. Its stated use cases are exactly this control's hard queries: blast radius of a vulnerability, whether all production binaries trace to a managed repository, which applications are missing SBOMs or attestations. Created by Kusari, Google, Purdue and Citi — there is a bank precedent to cite.

OpenVEX and vexctl

Specification plus tooling for creating and merging VEX documents; statements replay chronologically to compute current status. Trivy and other scanners consume VEX to filter findings, so suppression is applied by the scanner rather than argued in a spreadsheet.

SSVC

CISA and CMU SEI publish the decision trees, a calculator and a JSON schema, including a vector string format that records the full decision path. Adopt and calibrate rather than inventing a bank-specific scoring model.

Sigstore and policy-as-code

Cosign for signing and verifying in-toto attestations; an admission policy engine to evaluate provenance, scan attestations, VEX and waivers as one policy at the gate. The waiver becomes a policy input, not a manual override.

OSV and deps.dev

Machine-readable vulnerability data keyed to package versions, which is what makes SBOM-to-advisory matching automatable rather than a name-matching exercise.

What stays bank-built

The calibrated SSVC tree, the builder trust map, waiver budgets and approval tiers, the digest-to-running-instance index across four target platforms, and VSA expiry policy. Everything else should be adopted.

The seams AppSec owns

Each pillar's tooling defines controls at its own boundary. Nobody owns the space between two boundaries. Threat labels are from the SLSA v1.2 threat model.

S1 · Ingress → Build

Resolution integrity

Proves the build consumed only what the proxy screened. Without it a build can bypass ingress entirely and the ingress control means nothing downstream.

Evidence: resolved dependency list reconciled to proxy records.

Threats: (D) external parameters, (H) dependency confusion

S2 · Build → Inventory

Registration on emit

Every build output registers itself with its SBOM. No contract defined between build tooling and inventory tooling today, which is what makes the CVE blast-radius query unanswerable.

Evidence: digest present in inventory within the build window.

Prerequisite for the CVE clock

S3 · Build → Artefact

Attestation handover

Signed artefact plus provenance plus scan attestations is the only permitted exit from build tooling. Anything else cannot be promoted.

Evidence: signature and provenance verify against the registered builder key.

Threats: (E) build process, (F) artefact publication

S4 · Approval → Deploy

Approval binds to digest

Release approval must reference the exact artefact admitted. Approving a branch or version string leaves a substitution gap. Where deployment is ungated, the registry path is the enforcement point instead.

Evidence: admitted digest equals approved digest; protected-path pull permission restricted to gated deployers.

Threats: (G) distribution channel

S5 · Deploy → Runtime

Running inventory

What is actually running, at which digest, on which platform. Without this the control can prove what was approved but not what is live.

Evidence: reconciliation of running instances to admitted digests, across all four target platforms.

Blast radius, drift, and the regulatory question

What SLSA does not cover

State these explicitly. A control that implies SLSA closes them will fail its first serious review.

Malicious producer

Not addressable by SLSA controls. Covered by joiner vetting, access management and two-party review.

Code quality and vulnerabilities

SLSA says nothing about whether the code is secure. That is what the scanning disciplines above are for.

Reviewer collusion and bugdoors

Explicitly out of scope. Mitigated by rotation, sampling and independent review of high-risk changes.

Transitive dependencies

An artefact's level is independent of its dependencies' levels. Apply the framework recursively or accept the gap knowingly.

Platform insider at L3

Build L3 does not cover compromise of the build platform itself. Needs PAM, audit and two-person change on the platform.

Typosquatting and availability

Neither is addressed. The ingress proxy and the draft Dependency track are the relevant controls.

Path: FOSS dependencies

Java, Python, npm and Go. The chain is the same; what differs is where composition can be determined truthfully, how much of it survives the build, and whether reachability is answerable at all.

Licence scanning

A different discipline from vulnerability scanning with a different failure mode: licence problems are not discovered by an advisory feed, they are discovered by counterparties and regulators.

Declared, detected, effective

Declared is what the package metadata claims. Detected is what a scanner finds in the actual files. Effective is what applies after dual-licence choices and exceptions. Policy decisions must run on effective, and the three disagree often enough that using declared alone is not defensible.

Obligation depends on distribution

An internal service, a customer-facing web application, a distributed mobile app and customer-installed software carry materially different obligations from the same licence. The mobile path is where copyleft actually bites, because the binary leaves the bank.

Licences change between versions

Relicensing is real and increasingly common. The check is per package-version, never per package, and a version bump must re-run the evaluation rather than inherit the prior verdict.

Transitive obligations

The problematic licence is usually four levels down and arrived without anyone choosing it. Only the build-time resolved graph will show it, which is another reason the SBOM of record has to come from the build.

Notice generation

Attribution files are an output of the SBOM, generated per release, not maintained by hand. If your notice file is edited manually it is already wrong.

Tooling

ScanCode Toolkit and FOSSology for detection; OSS Review Toolkit to combine detection, policy evaluation and notice generation in a pipeline. Licence policy belongs in the same policy engine as everything else on this path.

Gate placement. Licence findings block at ingress for categorically prohibited licences, and at release for obligation-bearing ones, because obligations depend on the distribution mode and that is not known at ingress. This is the same deferred-decision shape as the vulnerability path: what is knowable at ingress is the licence identity; what is knowable only later is whether it matters.

Path: containers

Images behave differently from every other artefact in this control: most of their vulnerabilities are inherited rather than written, and the thing deployed is frequently not the thing that was scanned.

Two properties define this path. A tag is a mutable pointer, not an identity — so scanning app:1.4 proves nothing about what admission later pulls under that name. And most image CVEs are fixed by rebuilding on a current base, not by changing code — so remediation is a pipeline cadence problem rather than a developer backlog problem. Both change how the gate and the clock work.

Relationship to the FOSS layers. An image scan resolves OS packages well and application dependencies badly. The container path covers the base and OS layer; the application layer's composition comes from the build SBOM on the relevant language path. Neither is sufficient alone, and an image scan reported as complete coverage is the most common overstatement in this area.

The second clock: base image currency

The CVE clock in the control overview starts at advisory publication. This path needs a second, independent clock — and it is usually the one that actually drives remediation volume.

Why separate

Inherited, not authored

The majority of findings in a typical image come from OS packages the team never chose. No code change fixes them; a rebuild on a current base does. Treating these as application defects on a developer backlog is the standard failure, and it produces large queues that nobody can action.

Leading metric

Base image age

Time since the running image's base was last rebuilt. It predicts CVE exposure before the advisories arrive, and unlike finding counts it is actionable by one team with one pipeline.

Mechanism

Scheduled rebuild, not scheduled patching

Golden bases rebuild on a fixed cadence and on advisory triggers. Downstream images rebuild against the new base automatically where the pipeline allows it. The service team's involvement should be testing the result, not sourcing the fix.

Escape valve

Distroless and minimal bases

Fewer packages means fewer inherited findings and a smaller attack surface. The trade is debuggability and, for scratch images, that conventional scanners report nothing at all — see the Go layer.

Boundary

Where the clocks meet

An application-layer CVE runs on the CVE clock and is owned by the service team. An OS-layer CVE runs on the base currency clock and is owned by the platform. Every image finding should route to one of the two, and a finding that routes to neither is a gap in the ownership model rather than a triage problem.

Risks and gaps

C1

Mutable tags

A tag can be repointed after scanning and approval. The artefact verified at the gate and the artefact pulled by the node are then different things, and nothing in the chain detects it.

Fix: digests in deployment manifests; tags permitted only as human-readable aliases in non-production.

C2

Layer archaeology

A file deleted in a later layer remains present in the earlier one. Secrets removed by a subsequent RUN are still in the image and still extractable.

Fix: secret scanning across all layers, not the flattened filesystem; build secrets via mount rather than copy.

C3

Build tooling shipped to production

Single-stage builds leave compilers, package managers and credentials in the runtime image, expanding both attack surface and the finding count.

Fix: multi-stage builds as a standard; lint for it.

C4

Application layer invisible to image scanning

Image scanners resolve OS packages well and application dependencies poorly or not at all. A clean image scan over a fat jar or a Go binary says very little.

Fix: image SBOM and build SBOM are both required; the gate evaluates them together.

C5

Unapproved public base images

Pulling directly from public registries bypasses the golden set, and unofficial images carry both provenance and licence uncertainty.

Fix: registry allow-list at the network layer, so the control cannot be bypassed by a Dockerfile edit.

C6

Windows containers

Larger images, different scanner coverage, and licensing considerations the Linux path does not have. Coverage assumptions from Linux do not transfer.

Fix: assess scanner support explicitly for the Windows estate rather than assuming parity.

Licence considerations

OS packages carry obligations too

A base image bundles hundreds of packages under many licences. For internally deployed services this is usually low risk; for anything distributed to customers it is not, and the obligation attaches to the image rather than to the application.

Golden bases solve it once

Licence review on a small curated set of bases, refreshed on rebuild, is tractable. The same review across every team's ad-hoc base choices is not. This is a second strong argument for the golden set.

Notices for distributed images

Where images ship outside the bank, attribution must cover the OS layer as well as the application dependencies, generated from the image SBOM rather than assembled by hand.

First three moves

1. Golden base image pipeline

A small curated set, rebuilt on a cadence and on advisory triggers, owned by the platform. This is the highest-leverage control on the path and it reduces finding volume before any triage effort is spent.

2. Digest pinning end to end

Base images pinned in Dockerfiles, images pinned in deployment manifests. Without this the verification chain has a hole at the last step, whatever else is in place.

3. Attach attestations to the digest

SBOM, provenance and VEX as OCI referrers, verified at admission. This is what lets the evidence travel with the image and makes the promotion-path model work for containers.

Path: vendor binaries

Commercial software delivered as compiled artefacts — COTS applications, agents, libraries, appliances. No source, no build control, and a supplier who may or may not answer the questions this control asks.

Every other path in this control works by generating evidence. This one cannot: we do not run the build, so we cannot produce provenance — we can only require it, verify what arrives, and constrain what the artefact is permitted to do. The consequence is that the real gate sits in procurement, months before anything reaches the registry, and the technical controls are containment rather than verification.

SLSA position. Vendor artefacts sit at Build L0 by default, because nothing about their build is verifiable to us. A vendor supplying signed SLSA provenance moves to whatever level their builder supports — but that is their claim about their platform, not our verification of it. Record vendor-supplied provenance as evidence received, never as a level we have assured. The bank's own VSA for a vendor artefact should assert what we actually checked: signature validity, binary composition, and behavioural review.

Path: freeware and shareware

Utilities, developer tools, trial software and prebuilt binaries acquired without a contract, a supplier relationship or, often, a record that they exist.

This path carries the worst ratio of risk to attention in the whole control. There is no counterparty to make requirements of, no support commitment, frequently no signature, and — decisively — these binaries usually arrive on endpoints and build agents rather than through a pipeline. That places them inside the trust boundary the rest of this control depends on, while sitting outside every gate it defines.

Boundary with the FOSS path. A prebuilt binary of an open-source project — a release asset rather than a package-manager dependency — belongs on this path, not the FOSS one. The source being public does not mean the binary was built from it, and nothing links the two unless the project publishes provenance. Build from source and you are on the FOSS path; download the binary and you are here.

What we are actually dealing with

The category is heterogeneous, and the sub-types need different answers.

Freeware

Free, proprietary, no source. Common for niche utilities. Security posture is unknowable; the only real control is whether it is needed at all.

Shareware and trials

Free to evaluate, payment required for continued or commercial use. The risk is as much licence compliance as security: trial software in production is an audit finding waiting to happen.

Open-source release binaries

Source exists but was not used. Treat as binary unless built internally or accompanied by verifiable provenance.

Free tiers of commercial products

A vendor relationship exists but without contractual leverage. Terms can change unilaterally, including terms governing data handling.

Abandonware

Still functioning, no longer maintained, no route to remediation. Every finding is permanent by definition.

Developer tooling

The highest-risk subset, because it runs with developer privilege on machines with source access and credentials. Frequently installed without any approval at all.

Path: harvested source and forks

Upstream source pulled in through the FOSS harvester, modified, built internally, and — where possible — contributed back.

This path inverts the control. Everywhere else the bank is a consumer verifying someone else's claims. Here, the moment we modify and build, we become the producer. The SLSA producer requirements now apply to us, the artefact is no longer the upstream one, and the responsibility for its security moves inside the bank. That is a genuine capability — it is also the path where identity quietly breaks if the control does not handle it explicitly.

The core problem: identity divergence. Our build of a library at version 2.17.1 with three local patches is not 2.17.1, but every advisory feed, scanner and SBOM matcher will treat it as though it were. That produces errors in both directions — false positives where we patched ahead of upstream, and false negatives where an upstream fix has not been rebased in. Neither is visible without deliberate handling, and the second is the dangerous one.

Fork debt

Every local patch is a standing liability that grows with upstream distance. Measure it directly rather than inferring it from incidents.

Rebase lag

Releases behind upstream

The leading indicator. A fork three releases behind is carrying unapplied security fixes whether or not anyone has noticed, and the cost of catching up rises non-linearly.

Patch count

How far we have diverged

A handful of small patches is maintainable. Dozens means an internal maintainership nobody agreed to take on, and the exit cost keeps rising.

Patch age

Time since each patch was written

An old patch that has not been upstreamed is usually one of three things: unacceptable to upstream, never submitted, or forgotten. Each needs a different answer.

Upstream rate

Proportion of patches merged upstream

The health metric for the whole path. A low rate means the fork is permanent and should be resourced as a maintained internal product, or abandoned.

Exit plan

Every fork has an expiry

Forks are created with a stated intent: upstream it, replace it, or adopt it deliberately. A fork with no route out becomes an unowned internal dependency, which is the worst of both models.

Contributing back

Upstream-first should be the default: a merged patch is maintained by the community, a local patch is maintained by us forever. The route needs to be fast enough that engineers use it.

The embargo step is the one to get right. If an engineer finds and fixes a security bug in an upstream project, the ordinary contribution route is the wrong one — an open PR containing a security fix tells every attacker exactly what to exploit in every unpatched deployment worldwide, including ours. That path needs a named owner in AppSec, a coordinated disclosure route to the project, and an internal patch we can carry during the embargo period without publishing it. Build this before it is needed, because it will be needed at short notice.

Licence obligations

Modification changes the obligation

Several licences require modified files to carry a notice of change. Apache-2.0 and the GPL family both do, in different forms. Consuming unmodified and shipping modified are materially different positions.

Distribution is the trigger

Internal use of a modified copyleft component generally carries no source-provision duty; distributing the binary does. Mobile apps, customer-installed software and appliances are the paths where this bites.

Network use counts for AGPL

Under AGPL, offering the service over a network can trigger the source obligation without any binary leaving the bank. Flag AGPL components at harvest, not at release.

Notices must reflect the fork

Attribution generated from the SBOM has to describe the modified component and its origin, not the upstream release it started from.

Contribution grants rights

Submitting a patch licenses it under the project terms and may carry a patent grant. That is fine and intended, but it is a decision the bank makes once per project, with legal, rather than per engineer.

Harvest-time screening

Licence evaluation happens when source is harvested, because that is when the choice to depend on it is made. Discovering an incompatible licence at release is discovering it too late.

Risks and gaps

S1

Silent identity collision

The fork reports an upstream version it no longer matches, so scanners, SBOM consumers and advisory feeds all draw the wrong conclusion.

Fix: distinct internal identity in the SBOM with recorded upstream ancestry; VEX for every divergence.

S2

Unapplied upstream security fixes

The failure mode that matters. Upstream patches a vulnerability, our fork does not rebase, and the version string still looks current to everyone.

Fix: advisory matching on upstream identity is mandatory and cannot be suppressed by fork status alone.

S3

Invisible forks

Source copied into an application repository rather than harvested — vendored by hand — carries no fork record at all and will never be matched against an advisory.

Fix: detect copied third-party source in code scanning; route it onto this path retrospectively.

S4

Harvest without provenance

Source pulled from a mirror, a fork of the real project, or an unverified tag. The upstream identity is then an assumption rather than a fact.

Fix: harvest attestation recording repository, commit, signature status and time — treated as ingress evidence.

S5

Maintainership by accident

A fork nobody planned to own becomes a critical internal dependency with no maintainer, no test coverage and no exit route.

Fix: named owner and stated exit intent at fork creation; forks without either are closed or adopted deliberately.

S6

Disclosure through contribution

A public patch can leak internal architecture, or — worse — an unembargoed security fix.

Fix: automated sanitisation plus a separate embargo route with a named AppSec owner.

First three moves

1. Give forks a distinct identity in the SBOM

With upstream ancestry recorded. Until this exists, every fork is silently misreported to every tool that consumes our SBOMs, including our own gate.

2. Match advisories on upstream identity regardless

Then resolve with VEX. Erring towards false positives here is correct; the alternative is missing an upstream fix we never rebased.

3. Build the embargo contribution route now

It is needed at short notice, under pressure, and improvising it is how a coordinated disclosure becomes an uncoordinated one.

Treating risk findings

One repeatable shape for every finding: four treatments across three horizons. The shape matters more than any individual entry, because it makes findings comparable and makes gaps visible without anyone having to argue for them.

The four treatments are not alternatives to choose between. They answer different questions, and the empty cells are the finding's real risk position. A finding with only mitigations is being survived rather than managed. A golden path with no detection cannot tell you who is not on it. Detection with no golden path produces a backlog with nowhere to send people.

Using the model

One finding, one grid

Keep the four-by-three shape even when cells are empty. The empty cell is the point — it is a claim about what we currently cannot do, made visible.

Mitigations expire

Short-term mitigations get a review date. Still primary at the long horizon means the plan failed, which is a finding in itself rather than a status update.

MVPs need a kill criterion

Stated accuracy or value threshold and a decision date at the start. Pilots without one become permanent half-deployments that nobody will end.

Detection before enforcement

Enforcing a path you cannot measure punishes the visible and misses the rest. Sequence detection first wherever the choice exists.

Match new findings to known patterns

Most new technologies present an existing pattern in new clothing. Naming the pattern transfers the treatments and shortens the analysis.

Register is the review artefact

The grids are for working; the register is what goes to governance. Coverage columns, not progress percentages — they are harder to game and more honest.

Path: SDKs, IDEs and plugins

Developer desktop binaries — language SDKs and toolchains, IDEs, and the plugin ecosystems that extend them.

Two things make this path different from anything else in the control. The toolchain is a build input: a compromised SDK compromises every artefact built with it, and the SLSA model treats the builder's own dependencies as part of the trust boundary for exactly that reason. And IDE plugins execute with developer privilege — with access to source, credentials, cloud tokens and SSH keys — while being installed from marketplaces with weak publisher verification, on auto-update, with no pipeline anywhere in sight.

Where this sits relative to the other layers. The freeware path covers unmanaged tools generally; this path covers the specific population that participates in producing software. That distinction matters because these binaries sit inside the boundary that Build L2 and L3 claims depend on. An IDE plugin with repository write access is closer to the source-integrity controls than to endpoint management, even though it is installed like any other desktop app.

Risks and gaps

D1

Compromised toolchain

A malicious or tampered SDK injects into everything it builds, and no amount of scanning the output reliably detects it. Historic precedent exists for exactly this, distributed through unofficial mirrors of a popular IDE.

Fix: internal mirror, digest pinning, signature verification at ingest, and toolchain identity recorded in provenance.

D2

Extensions with full developer authority

An extension can read source, exfiltrate credentials, modify code before commit, and invoke agent tooling. Marketplace review is not a security control.

Fix: allow-list with publisher verification; pinned versions; installed-extension telemetry reconciled against it.

D3

Silent auto-update inside the boundary

A trusted extension becomes malicious at version n+1 through publisher account compromise or sale of the project, and updates arrive without review.

Fix: updates flow through the internal mirror; a version change is a reviewable event, not a background task.

D4

Typosquatted extensions

Impersonating names and inflated install counts make the wrong choice a single click from a search result.

Fix: developers install from the internal catalogue, not from marketplace search.

D5

Local builds reaching production

An artefact built on a laptop has no provenance, no gate and no record, yet can be pushed to a registry by anyone with credentials.

Fix: registry write restricted to build platform identities. This is a registry permission, and it is the single most effective control on this path.

D6

Toolchain sprawl

Dozens of SDK builds in use means an unbounded patch population and inconsistent provenance across the estate.

Fix: curated set with a version floor; projects pin within it rather than to arbitrary builds.

D7

Code egress via assistant extensions

Extensions that send source to external services for completion or analysis move code outside the bank as a routine part of their operation.

Fix: assess each one explicitly against data handling requirements; approve the endpoint, not just the extension.

D8

Licence drift in runtimes

Distribution terms for some widely used runtimes have changed materially after organisations adopted them, creating commercial exposure with no technical signal.

Fix: licence position reviewed per distribution at catalogue entry and on major version changes.

Where this path is heading

The long-horizon answer changes the shape of the problem rather than tightening the existing controls.

Managed development environments

Ephemeral, centrally defined workspaces — container-based or remote — make the toolchain a versioned, inspectable artefact rather than the state of someone's laptop. They also remove the local-build problem by construction.

Devcontainer definitions as code

Toolchain and extension set declared in the repository, reviewed like any other change, and reproducible. This is the same move as pinning base images, applied to the development environment.

Build agents converge with desktops

Once both draw from the same curated toolchain set, the provenance story becomes consistent and the patch population becomes finite.

First three moves

1. Restrict registry write to build platform identities

Closes the local-build route to production. One permission change, and it does more than any desktop control on this list.

2. Inventory installed extensions

Reconciled against an allow-list. Expect the first run to be uncomfortable, and expect to find AI assistant extensions nobody assessed.

3. Mirror and pin the toolchain set

Then record toolchain identity in build provenance, which turns a desktop hygiene exercise into part of the verification chain.
